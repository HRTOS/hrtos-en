OVERVIEW

Interrupts in a Real-Time Operating System

Interrupts provide a mechanism for responding to hardware events without waiting for the normal task execution flow.

On 8051 microcontrollers, interrupts are closely associated with CPU execution state, register banks, interrupt priority levels, and the processor's stack mechanism.

HRTOS takes these architectural characteristics into account when coordinating interrupt execution and task scheduling. Its interrupt model defines how interrupt handlers operate, how nested interrupts are handled, and where task-level scheduling operations are permitted.

A key design consideration is maintaining a clear boundary between interrupt-level processing and normal task-level kernel services.

EXECUTION FLOW

Interrupt Execution Sequence

An interrupt event enters the processor's interrupt handling path. After the handler completes, execution returns according to the processor and operating system state.

01

Hardware Event

A timer, external signal, serial interface, or other peripheral generates an interrupt request.

02

Interrupt Entry

The 8051 CPU enters the corresponding interrupt service routine according to its interrupt configuration.

03

ISR Execution

The interrupt handler performs the required event processing under the applicable interrupt nesting rules.

04

Interrupt Return

The handler completes and execution resumes through the configured interrupt and scheduling mechanisms.

The exact return and scheduling path depends on interrupt nesting state and the kernel execution context.

NESTED INTERRUPTS

Nested Interrupt Handling

Nested interrupts allow a higher-priority interrupt to be serviced while a lower-priority interrupt handler is executing, subject to the 8051 interrupt configuration and HRTOS rules.

HRTOS accounts for interrupt nesting depth as part of its interrupt execution model. This requires careful management of execution state and strict separation of operations that are valid at different interrupt levels.

The system supports nested interrupt execution, but nested interrupt handlers must follow specific kernel interaction restrictions.

Interrupt Priority

Interrupt priority configuration determines whether an interrupt can preempt another interrupt handler under the 8051 interrupt model.

Nesting Depth

HRTOS tracks interrupt nesting information so that interrupt-related execution rules can be applied at the appropriate level.

Execution State

Interrupt handlers must preserve the execution assumptions required by the operating system and application code.

KERNEL RULES

Interrupt-Level API Restrictions

Not every kernel operation is valid from every interrupt nesting level.

HRTOS distinguishes between interrupt-level processing and task-level operations that may affect scheduling or task readiness.

In particular, nested interrupt handlers must not invoke scheduling or task wake-up APIs. These operations are restricted to execution contexts where the kernel can safely coordinate task state transitions.

Operation Nested ISR Notes
Interrupt-local processing Permitted Subject to application and hardware execution constraints.
Priority-related operations Subject to rules Only priority-related changes allowed by the configured interrupt model should be used.
Task wake-up APIs Not permitted Nested interrupt handlers must not invoke task wake-up operations.
Scheduling APIs Not permitted Scheduling operations must not be invoked from nested ISRs.

Always consult the HRTOS API documentation for the exact restrictions of individual functions.

8051 CPU RESOURCES

Register Bank Considerations

The 8051 register-bank organization is an important part of the HRTOS execution model.

The MCS-51 architecture provides four register banks, each containing the R0-R7 register set. Register-bank selection is controlled through the processor status register.

HRTOS takes advantage of this hardware feature in its execution context design. Fast tasks use dedicated register-bank resources, reducing the amount of context information that must be handled for their execution model.

Interrupt handlers also need to respect register-bank usage and preservation rules. The selected register bank must be consistent with the configured interrupt and task execution conventions.

Hardware Register Banks

Four register banks are available in the classic 8051 register organization.

Fast Task Contexts

HRTOS provides dedicated register-bank resources for its fast task mechanism.

Interrupt Context

Interrupt execution must account for register-bank selection and context preservation requirements.

Platform Dependence

Register-bank availability and behavior should be verified against the specific 8051-compatible device.

TASK COORDINATION

Interrupt-to-Task Coordination

Interrupt handlers and application tasks have different execution responsibilities. A clear boundary helps organize event processing.

Interrupt handlers are generally responsible for responding to hardware events and performing the necessary time-sensitive processing. More extensive application logic can be organized in task-level code.

HRTOS provides task synchronization and communication mechanisms that can be used to organize cooperation between system components. The exact APIs available from interrupt context depend on the interrupt nesting level and API-specific restrictions.

Applications should therefore keep interrupt handlers focused and use supported task-level mechanisms for work that does not need to execute directly in the ISR.

Hardware Event Handling

Capture or acknowledge hardware events in the appropriate interrupt handler.

Task-Level Processing

Organize longer application operations in normal task execution.

Synchronization

Use supported synchronization and communication mechanisms to coordinate application components.

DEVELOPMENT GUIDANCE

Practical Considerations

Correct interrupt integration requires attention to both the processor architecture and the operating system's execution rules.

Keep ISRs Focused

Avoid unnecessary processing in interrupt handlers. Move application-level work into tasks where appropriate.

Respect Nesting Rules

Do not invoke scheduling or task wake-up APIs from nested interrupt handlers.

Check Register Usage

Verify register-bank assignments and context preservation when integrating application ISRs.

Measure on Target Hardware

Evaluate execution timing using the actual microcontroller, compiler, and clock setup.
