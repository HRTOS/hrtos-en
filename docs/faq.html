General

About HRTOS

Basic information about the operating system and its intended application environment.

01

What is HRTOS?

HRTOS is a real-time operating system designed for 8051 and MCS-51 microcontrollers. It provides task scheduling, interrupt management, synchronization, inter-task communication, and other system services.

It is intended to help developers build structured embedded applications on resource-constrained 8-bit microcontrollers.

02

What does HRTOS stand for?

HRTOS stands for Hard Real-Time Operating System. The name reflects the project's focus on deterministic scheduling and predictable real-time behavior.

Actual timing guarantees depend on the hardware, system configuration, application workload, and the design of individual tasks and interrupt handlers.

03

Which processors does HRTOS support?

HRTOS is designed for the 8051 and MCS-51 microcontroller architecture.

It is intended for compatible 8051-family devices, including supported STC microcontrollers. Actual compatibility depends on memory resources, compiler support, and device-specific requirements.

04

Is HRTOS limited to one microcontroller model?

No. HRTOS targets the broader 8051/MCS-51 architecture rather than a single chip model.

However, not every 8051-compatible device has identical memory capacity, peripherals, or hardware behavior. Developers should verify the requirements of their target device.

Development

Development Environment

Questions about compilers, hardware requirements, and project integration.

Which compiler is used by HRTOS?

HRTOS V4.0.0 is designed for the Keil C51 development environment.

The compiler configuration, memory model, linker settings, and target-device settings should be configured according to the project requirements.

What are the minimum memory requirements?

The full HRTOS configuration requires at least:

  • CODE memory: 8 KB or more
  • XDATA memory: 1 KB or more

These are baseline requirements for the full system configuration. Actual memory consumption depends on enabled modules, task configuration, application data, and stack allocation.

Can HRTOS run on a classic 8051 with limited RAM?

The full HRTOS configuration has specific XDATA requirements. Devices with very limited external data memory may not be suitable for the complete configuration.

A cooperative scheduling option is available for applications that need a more constrained system configuration. Developers should select the appropriate configuration for their hardware.

Can I use HRTOS with an STC microcontroller?

HRTOS is designed for the 8051/MCS-51 ecosystem and supports compatible STC devices that meet its technical requirements.

Before starting a project, check the device's CODE memory, XDATA capacity, timer resources, interrupt architecture, and compiler compatibility.

How do I integrate HRTOS into an existing project?

Start by reviewing the installation instructions and the system configuration. Then integrate the required HRTOS libraries and interface files into the Keil C51 project.

After configuring the system, initialize HRTOS, register application tasks, and verify the scheduling behavior before adding more complex application functions.

See the Installation Guide and Getting Started Guide for more information.

Task Management

Scheduling and Tasks

Common questions about task execution, priorities, and scheduling behavior.

Does HRTOS support preemptive scheduling?

Yes. HRTOS provides preemptive task scheduling. Tasks are managed according to their configured scheduling priorities and system scheduling rules.

This allows higher-priority tasks to respond without waiting for lower-priority tasks to voluntarily yield the processor.

How many tasks can HRTOS manage?

The standard HRTOS V4.0.0 configuration supports up to 16 normal tasks. It also provides a separate fast-task mechanism with support for up to 2 fast tasks.

The actual number of tasks available in an application depends on the system configuration and memory resources.

What is the difference between normal tasks and fast tasks?

Normal tasks use the standard task execution and scheduling mechanism. Fast tasks use a dedicated execution mechanism designed for shorter task-switching paths.

Fast tasks are useful for selected time-sensitive operations. They should be used according to the system's configuration and execution rules.

How should I choose task priorities?

Assign priorities according to the application's response-time requirements.

  • Give higher priority to time-critical operations.
  • Keep background processing at lower priorities.
  • Avoid unnecessary priority differences.
  • Consider shared resources and blocking behavior.

Priority assignment should be evaluated together with task execution time, interrupt activity, and application timing requirements.

Can a task wait for an event or a message?

Yes. HRTOS provides synchronization and inter-task communication mechanisms, including events, semaphores, mutexes, mailboxes, and message queues.

These mechanisms allow tasks to coordinate execution without relying entirely on continuous polling.

Interrupt Management

Interrupts and Real-Time Behavior

Important considerations when working with interrupt-driven applications.

Does HRTOS support interrupt management?

Yes. HRTOS provides interrupt-related mechanisms for embedded applications that require predictable interrupt handling and task coordination.

The interrupt model is designed around the characteristics of the 8051 architecture.

Can I perform task scheduling inside an ISR?

Interrupt service routines should be kept short and should follow the HRTOS interrupt usage rules.

In particular, nested interrupt handlers should not directly call scheduling or task-wakeup APIs. Use the documented interrupt-safe mechanisms to coordinate with application tasks.

Does HRTOS support nested interrupts?

HRTOS takes the interrupt priority and nesting characteristics of the 8051 architecture into account.

Nested interrupt behavior depends on the target device's interrupt capabilities and the configured interrupt model. Follow the system documentation when implementing nested interrupt handling.

Does HRTOS guarantee hard real-time behavior?

HRTOS is designed for deterministic real-time operation on 8051 microcontrollers. Its scheduling and interrupt mechanisms are intended to support applications with predictable timing requirements.

A hard real-time guarantee must be established for the complete application, including worst-case execution time, interrupt latency, blocking time, hardware behavior, and scheduling configuration. Developers should measure and validate these conditions on the actual target system.

System Components

Communication and Components

Questions about built-in system services and application-level functionality.

Does HRTOS provide inter-task communication?

Yes. HRTOS provides communication mechanisms such as mailboxes and message queues, allowing tasks to exchange data and coordinate operations.

The appropriate mechanism depends on the application's data flow and synchronization requirements.

Does HRTOS support mutexes and semaphores?

Yes. HRTOS provides synchronization mechanisms including semaphores and mutexes.

Mutex support includes priority inheritance to help address priority inversion when tasks share resources.

Does HRTOS include a Shell?

HRTOS provides a Shell extension for system interaction and debugging. It includes commands for inspecting system information and task-related status.

Available commands depend on the enabled Shell configuration.

Does HRTOS support Modbus RTU?

HRTOS provides a Modbus RTU slave extension for embedded communication applications.

Supported function codes include FC01, FC03, FC05, FC06, and FC10.

Can I add my own drivers and application modules?

Yes. Developers can integrate hardware drivers and application modules according to their project requirements.

The HRTOS website also provides hardware information, driver resources, and application examples to help developers build complete embedded systems.

Visit the Drivers and Examples sections for additional resources.

Troubleshooting

Common Development Issues

A few practical checks that can help identify common integration and runtime problems.

01

HRTOS does not start correctly

Check the system initialization sequence, project configuration, library integration, and linker settings.

Also verify that the selected device provides sufficient CODE and XDATA memory.

02

Tasks do not execute as expected

Review task registration, task priorities, scheduling configuration, and task state.

Check whether tasks are waiting for events, messages, or other synchronization conditions.

03

Unexpected timing behavior

Verify the oscillator frequency, timer configuration, interrupt load, and application execution time.

Measure timing on the actual target hardware instead of relying only on theoretical estimates.

04

Memory-related problems

Review the memory model, XDATA allocation, stack usage, task configuration, and enabled system modules.

Make sure that application data and system resources do not exceed the available memory capacity.
