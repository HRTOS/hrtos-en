Interrupt Latency

Interrupt handling is a fundamental part of real-time system behavior. This page describes HRTOS interrupt execution measurements and the considerations involved in handling interrupts on 8051 microcontrollers.

OVERVIEW

Interrupt Handling in HRTOS

Interrupts provide a mechanism for responding to external events and time-critical hardware conditions. HRTOS is designed to work with the interrupt architecture of the 8051 family while maintaining coordinated task scheduling and system resource management.

Interrupt Execution

Interrupt service routines handle hardware events directly. Their execution time contributes to the overall response behavior of the system.

Nested Interrupts

Nested interrupt handling allows a higher-priority interrupt to be serviced while a lower-priority interrupt is executing, subject to the MCU interrupt configuration.

Task Coordination

Interrupt events can be coordinated with task-level processing through the kernel's scheduling and synchronization mechanisms.

EXECUTION MODEL

Interrupt Execution Flow

Interrupt handling involves hardware interrupt recognition, CPU context handling, execution of the interrupt service routine, and return to the interrupted execution context.

01

Hardware Event

A peripheral or external signal generates an interrupt request.

02

Interrupt Recognition

The 8051 interrupt controller and CPU determine whether the request can be serviced.

03

ISR Execution

The corresponding interrupt service routine executes and handles the event.

04

Return

The CPU returns from the interrupt and resumes the appropriate execution context.

INTERRUPT PRIORITY

Nested Interrupt Handling

Nested interrupts provide a way to handle events with different urgency levels. The actual behavior depends on the interrupt priority configuration and the capabilities of the target 8051-compatible MCU.

Priority-Based Execution

When nested interrupts are enabled, an interrupt with sufficient priority may interrupt a currently executing lower-priority interrupt service routine. This allows urgent hardware events to receive attention without waiting for the lower-priority routine to finish.

The measured nested interrupt execution time on the STC12C5A60S2 test platform was 11.917 us under the tested conditions.

ISR and Kernel API Considerations

Interrupt service routines should remain short and predictable. Operations that may trigger task scheduling or wake-up processing must follow the kernel's interrupt-context rules.

In particular, nested interrupt handlers should not call scheduling or task wake-up APIs. Priority-related operations must also respect the target MCU's interrupt priority configuration.

ENGINEERING CONSIDERATIONS

Designing Predictable Interrupt Handling

Interrupt performance is determined by both hardware behavior and software implementation. Reliable real-time behavior requires attention to the complete interrupt execution path.

Keep ISRs Short

Perform only the operations required to handle the immediate hardware event. Move longer processing tasks to normal task context whenever practical.

Control Nesting Depth

Nested interrupts increase execution complexity and resource usage. Configure interrupt priorities and nesting behavior according to application requirements.

Respect Execution Context

Kernel services must be used according to their execution-context requirements. Avoid invoking scheduling operations from unsupported nested interrupt contexts.

Measure on Target Hardware

Interrupt timing varies with MCU architecture, clock frequency, compiler output, peripheral configuration, and ISR implementation.
